# File formats in Glimt

This page lists the file formats Glimt can show, how they are shown, and what Glimt deliberately
does not do. Glimt only reads the file you preview. It never runs code, installs anything, or
fetches anything from the network, not even for formats such as scripts, profiles, or configuration files.

## How to read the list

Each format has a row in the [list at the bottom](#all-formats). The columns mean:

- **Format**: the name of the format. A format can have its own dialects and variants.
- **Extensions**: which files Glimt recognizes. `.ext` is a file extension, and a name without a dot,
  such as `Dockerfile`, is an exact file name.
- **Status**: how well Glimt supports the format (see the table below).
- **Fixtures**: example files you can look at. Files under `Showcase/` are also in the app's
  examples menu. Files under `Cases/` are used to test broken or unusual files.
- **Comment**: what you see, what is not supported, and which extensions clash with other formats.

| Status | Meaning |
|---|---|
| Supported | Every listed file is shown with a view made for the format |
| Partial | Only some of the extensions have a dedicated view, or the format is shown as a closely related format |
| Recognized (Raw) | Glimt recognizes the file but shows it as plain text |
| Missing | Glimt does not support the format yet. Support may come later |
| Excluded | The format cannot be supported on macOS |

## Views

Glimt shows a file in one or more views. Which views are available depends on the format and on what
Glimt could read from that particular file.

| View | Shows |
|---|---|
| Source | The source text with syntax highlighting |
| Rendered | The finished result, for example Markdown as formatted text or a Mermaid diagram |
| Tree | The content as a tree of keys, values, and parts |
| Pretty | Structured data reformatted with indentation |
| Table | Rows and columns, for example CSV, logs, and archive contents |
| Diff | Changes in a diff or patch, with added and removed lines marked |
| Raw | The file's text exactly as it is |
| Hex | The file's bytes in hexadecimal form |

In the **Formats & Views** setting you can choose the order, the default view, and which views to show
for each format. If none of your chosen views fits, Glimt shows Raw or Hex instead.

## Format groups

| Format group | Examples | Views |
|---|---|---|
| Source code | Swift, Python, C/C++, JavaScript, shell scripts, Dockerfile, web server configuration, and many more | Source, Raw, Hex |
| Markdown | Markdown, R Markdown | Rendered, Source |
| Mermaid | `.mmd`, `.mermaid`, and Mermaid code blocks in Markdown | Rendered, Raw. Unsupported diagrams are shown as source text |
| Graphviz/DOT | `.dot`, `.gv` | Source, Raw, Hex. The graph is not drawn |
| Structured data | JSON, YAML, XML, GeoJSON, and property lists | Tree, Pretty, Raw. Binary property lists are shown in Hex |
| JSON Lines | `.jsonl`, `.ndjson` | Tree, Raw |
| ZIP | `.zip` | Table, Hex. Shows the contents without extracting anything |
| Configuration | TOML, INI, `.env`, Java Properties, Windows Registry files (`.reg`) | Source, Tree, Raw |
| CSV/TSV | `.csv`, `.tsv` | Table (default), Raw |
| Logs | Syslog, JSON logs, CEF/LEEF, access logs, Kubernetes, logfmt, and more | Table, Tree, Raw when the content can be parsed |
| Diff/Patch | Unified diff and Git diff | Diff, Raw |
| Other text | Text formats without a view of their own | Raw, sometimes Hex |
| Unknown binary files | Files Glimt does not recognize | Hex |

## When another app shows the file

Quick Look chooses which app gets to preview a file. If another installed app also handles the same
file type, Finder may choose it instead of Glimt. Some extensions are also shared by several
formats, for example `.m` (MATLAB and Objective-C) and `.ts` (TypeScript and MPEG video). In those
cases the content decides how Glimt shows the file. The comment for each format says so.

## For developers

The list is maintained by hand. `scripts/format-parity.py` derives Status and the summary from the
product catalog `InspectorCore/Sources/InspectorCore/Resources/formats.json`. Technical details live
in hidden HTML comments in the Comment column:

- `` Catalog: `id`. `` links the row to the catalog. Several rows can share an id.
- `Manual status: <reason>` locks Status when the extensions do not reflect the actual support.
- `` Evidence `id`: E2 … E5 `` are reported verification results. They change only after new verification.

To add a format:

1. Add a row in alphabetical order with Status `Missing`. Fixtures may be `—`.
2. Run `python3 scripts/format-parity.py --enrich` and then `--check`.
3. Once the format exists in `formats.json`: add `` <!-- Catalog: `id`. --> `` to the comment and
   link the format's showcase and fixtures. Run step 2 again.

`--explain` shows what each status is based on. Full support requires the format to pass `make test`
with its own fixtures. [Fixtures](../../Fixtures/README.md) describes the example files and
[Development](../../README.md#development) describes how to build.
